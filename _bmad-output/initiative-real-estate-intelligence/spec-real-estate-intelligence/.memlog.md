- (decision) Why: fragmented public listings let a user find a listing but not read a market; the
  product is the vision of a normalized, historical base with a deterministic, dated,
  source-traceable intelligence layer in which models route and explain but never compute; it is
  also a portfolio piece whose differentiator is modelling quality, not listing volume; the
  foundation phase makes contracts cheap to fix now (brief 1, 2, 11; PRODUCT.md).
- (capability) CAP-1 [MVP data] intent: collect listings from each permitted source on a schedule,
  within its terms of use, access policy, rate limits and licensing. success: a collection run over
  the synthetic dataset and each configured source is idempotent, resumes from its checkpoint after
  a restart, backs off when the source rate-limits it, shuts down gracefully and records what it
  collected, changed and failed (brief 3.8, 4.8, 5; Operations artboards).
- (capability) CAP-2 [MVP data] intent: store collected content as a raw snapshot before parsing, so
  data can be reprocessed and audited without collecting again. success: every normalized listing
  value traces to a stored raw snapshot; re-parsing stored snapshots updates the normalized data
  without one request to the source (brief 3.11; Listing and Operations artboards).
- (capability) CAP-3 [MVP data] intent: normalize parsed listings into distinct Property and Listing
  records with canonical attributes and a structured location. success: a listing holds property
  type, asking price, area, bedrooms, bathrooms, parking spaces and features in canonical form where
  the source gives them, and a location on the hierarchy country, state, city, zone, neighborhood,
  street block with coordinates where available; each value carries source, source URL and
  collection time (brief 4.1, 4.4, 4.7; screens.md).
- (capability) CAP-4 [MVP data] intent: decide which listings advertise the same physical property
  and show why. success: each match stores its probability and the evidence per reason; fixture
  listings of one property resolve to one Property holding several Listings; a low-confidence match
  stays separate or enters review instead of merging (brief 4.3; Property and Review artboards).
- (capability) CAP-5 [MVP data] intent: record a change to a listing as an event, so the evolution
  of a listing and of its price can be reconstructed. success: replaying a fixture in which a
  listing is created, repriced, re-described, removed and seen again yields ListingCreated,
  ListingPriceChanged, ListingDescriptionChanged, ListingRemoved and ListingReappeared in order with
  dates and previous values, and no earlier value is lost (brief 4.2, 7).
- (capability) CAP-6 [MVP reading] intent: search the properties of a place with filters and order

- (capability) CAP-11 [NL increment] intent: route each request by a typed, auditable intent
