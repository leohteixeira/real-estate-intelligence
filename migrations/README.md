# Migrations

Migrations are versioned SQL files, applied in lexicographic order by `scripts/migrate.sh`. The
decision to use explicit SQL, with no ORM, is recorded in
[`../specs/adrs/0003-persistence-driver-and-migrations.md`](../specs/adrs/0003-persistence-driver-and-migrations.md).

## Naming convention

```text
NNNN_<context>_<description>.sql
```

`NNNN` is a four-digit sequential counter, never reused. Number blocks are allocated as follows:

| Range       | Owner         |
| ----------- | ------------- |
| `0000–0999` | `platform`    |
| `1000–1999` | `properties`  |
| `2000–2999` | `market`      |
| `3000–3999` | `comparables` |
| `4000–4999` | `collection`  |
| `5000–5999` | `locations`   |
| `6000–6999` | `ask`         |
| `7000–7999` | `alerts`      |
| `8000–8999` | `audit`       |
| `9000–9999` | `identity`    |

## Rules

- Dates and timestamps are stored in UTC (`timestamptz`).
- Each bounded context owns one schema. No foreign key or join crosses a context schema.
- Identifiers are UUIDv7 values generated by PostgreSQL 18 and constrained at the database edge.
- External identifiers (source + id at the source) carry a uniqueness constraint, so that ingestion
  is idempotent.
- The `postgis` and `vector` extensions are available in the Compose image but are **not** enabled:
  the migration that needs one of them runs the corresponding `CREATE EXTENSION` and justifies the
  need.
- `platform.outbox` delivery claims are leases. Database time owns their expiry, and only the
  current claim identifier may mark a row published or release it.
- `platform.inbox` records a stable logical consumer name with an event identifier in the same
  transaction as the consumer effect.
- Published outbox rows are retained for seven days and consumed inbox markers for thirty days.
  The worker removes one deterministic batch of at most 1,000 rows per store every five minutes;
  an inbox marker remains while the matching outbox event is still unpublished. Maintenance uses
  database time, `SKIP LOCKED`, independent transactions and active cancellation on shutdown.
- `platform.idempotency_key` is only the bounded storage foundation. Reservation and replay rules
  are defined by the first public command that uses it.

## Initial property ingestion

`1001_properties_create_initial_properties.sql` owns the initial single-listing aggregate in the
`properties` schema. Property and Listing IDs are distinct UUIDv7 values. The durable source/listing
identity is unique, independent of expiring inbox markers. Immutable canonical incoming facts retain
their original provenance; a separate disposition stores `initial`, `pending-history` or
`pending-correction`. Later verified facts are not yet projected into history. Money is constrained
to safe-integer BRL cents. No foreign key or query crosses into Collection or Locations.

`4008_collection_add_parsed_event_evidence.sql` stores Collection-owned strict canonical parsed
publication evidence, written atomically with initial/paged collection or reparse state and outbox.
It verifies event time and values without depending on retained outbox rows or inventing legacy
evidence. Update triggers protect original evidence; deletion remains possible for the later
ADR 0015 suppression capability. Properties verifies it only through the Collection facade.

## Synthetic Locations reference

`5001_locations_create_place_hierarchy.sql` owns `locations.place`, reference metadata and
undirected neighborhood adjacency. It seeds exactly twenty places: the unchanged original eighteen
plus two fictional blocks for Bela Vista / Avenida Exemplo and Vila Mariana / Rua Cenário Um.
Supplementary blocks retain prepared ranges `100–199`, null coordinates and zero prepared counts.
The synthetic metadata timestamp is UTC; it is not a freshness claim about real geography.

Each internal ID is a database-generated UUIDv7; the separately unique public slug remains the
HTTP identity. The migration runner applies the seed once, preserving internal/public IDs on
replay. Composite own-schema foreign keys and strict parent-kind checks enforce all six levels
and prevent cycles. SQL checks enforce integer safe inclusive ranges without rounding fractional
input, finite coordinate pairs, block-only metadata and valid neighborhood-only adjacency. One
ordered undirected pair produces both read directions and prohibits duplicate/self edges.

`locations.valid_reference_name` uses the explicit ECMAScript trim whitespace set for both
display names and street names, including tabs, line breaks and Unicode spaces. Trimmed values
must contain 1–200 characters; whitespace-only values cannot be persisted and break hydration.

No foreign-schema joins or keys, address-query storage, unit/complement fields, PostGIS extension,
business events or mutation routes are introduced. Properties stores its initial resolved-place
snapshot through the facade; historical five-crumb snapshots are not rewritten by this migration.
Use `pnpm run test:integration:locations` after the build for real constraint, replay and HTTP tests.
